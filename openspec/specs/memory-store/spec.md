# memory-store Specification

## Purpose

Store executable memory as an OKF v0.2 bundle at `.context/`: one markdown file per concept, typed frontmatter, a generated reverse index beside metrics (not in the bundle), and optional monorepo sharding so package-local concepts land in the shard that owns their pins.

## Requirements

### Requirement: OKF v0.2 concept bundle

The system SHALL store memory as an OKF v0.2 bundle at `.context/`, one markdown file per concept, where concept identity is the file path relative to `.context/` (without `.md`) and the markdown body carries the prose why.

#### Scenario: Concept written to the bundle

- **GIVEN** an agent has a why to record for `src/billing/PaymentGateway.ts`
- **WHEN** `repocodex write` accepts the concept
- **THEN** a single markdown file is created under `.context/` with OKF frontmatter (`type` required)
- **AND** the directory `index.md` catalog and `log.md` are updated in the same operation

#### Scenario: Unknown frontmatter keys are preserved

- **GIVEN** a concept containing producer-defined extension keys
- **WHEN** any RepoCodex component rewrites the file
- **THEN** unknown keys are preserved byte-for-byte per OKF conformance

### Requirement: Concept types

The system SHALL author `TechnicalDecision`, `InvariantContract`, `BusinessWorkflow`, and `GuardrailDecision`. The schema SHALL NOT enumerate OKF types as a closed set that rejects the document. A consumer load SHALL keep unknown `type` values. A concept that pins code SHALL pass the write gate; an unanchored typed page SHALL be loadable and SHALL NOT be reverse-indexed.

#### Scenario: Workflow concept spans packages

- **GIVEN** a business flow touching `api`, `billing`, `ledger`, and `notify` packages
- **WHEN** an agent writes a `BusinessWorkflow` concept
- **THEN** the concept carries one anchor per participating site, each attesting independently

#### Scenario: Guardrail concept pins enforcement config

- **GIVEN** a negative architectural rule enforced by import-linter
- **WHEN** an agent writes a `GuardrailDecision` concept
- **THEN** the concept anchors the enforcing tool's config file, so weakening the rule drifts the anchor
- **AND** anchors are stored as extra keys on that file

### Requirement: Frontmatter extensions

The system SHALL define and validate the extension fields `verification` (required when the concept pins code), `claims` (required when prose states checkable literals), `supersedes` and `rationale` (required on why-change). The root catalog SHALL declare `okf_version`, not `format_version`. A missing optional family SHALL NOT cause a concept to be rejected.

#### Scenario: Why-change without supersedes is rejected

- **GIVEN** an existing stable concept whose why is being changed
- **WHEN** the agent writes the replacement without `supersedes` and `rationale`
- **THEN** the write is rejected with a machine-readable reason

### Requirement: Committed reverse index

The system SHALL maintain `.repocodex/reverse-index.md` as a generated, committed artifact mapping source paths to concept paths, regenerated by the engine on every accepted write or reanchor. It SHALL NOT be written under `.context/`. Regeneration SHALL remove any leftover `.context/**/reverse-index.md`. Unanchored concepts SHALL NOT appear in the map.

#### Scenario: Index stays in sync

- **GIVEN** an accepted `repocodex write` that adds a new pinned path
- **WHEN** the write completes
- **THEN** the reverse index includes the new mapping in the same change
- **AND** `.context/reverse-index.md` does not exist

#### Scenario: Out-of-sync index fails CI

- **GIVEN** a PR whose anchors and reverse index disagree
- **WHEN** the required CI check runs
- **THEN** the check fails with an index-sync error

### Requirement: Monorepo sharding

The system SHALL support `.context/` directories that mirror the source tree, with package-local concepts stored near the packages they pin, cross-cutting pages at the root, and per-shard reverse indexes at `.repocodex/reverse-index/<escaped-context-parent>.md`.

#### Scenario: CI attests only affected packages

- **GIVEN** a monorepo with sharded `.context/` directories
- **WHEN** a PR touches files in one package
- **THEN** validation attests only concepts whose pinned paths intersect the diff

### Requirement: Accepted writes land in the owning shard

The system SHALL write each accepted concept into the `.context/` shard that owns its pinned paths — the deepest mirrored bundle whose directory contains them — rather than always into the shallowest discovered bundle, and SHALL place cross-cutting concepts whose pins span shards at the root bundle. The reverse index of the receiving shard SHALL be regenerated on acceptance.

#### Scenario: Package-local concept lands in the package shard

- **GIVEN** a monorepo with a `.context/` bundle at the root and another mirroring `packages/billing/`
- **WHEN** a concept pinning only files under `packages/billing/` is accepted
- **THEN** the concept file is written into the `packages/billing/.context/` shard
- **AND** that shard's reverse index includes the new mapping

#### Scenario: Cross-shard concept lands at the root

- **GIVEN** a `BusinessWorkflow` concept with anchors in two different shards
- **WHEN** the write is accepted
- **THEN** the concept is written to the root bundle and each affected shard's reverse index reflects its pins

### Requirement: Provenance uses OKF sources objects

`sources` SHALL be a list of mappings. Each entry SHALL include `resource` (a URI, a bundle-relative path, or a scope descriptor). Optional `id`, `title`, `author`, `usage_count`, and `last_modified` MAY appear. A string list SHALL NOT be written. Bootstrap provenance SHALL put the evidencing commit or file in `resource`, not as a bare `commit:` token. Body footnotes keyed to `sources[].id` MAY attribute a claim; the engine SHALL NOT require footnotes.

#### Scenario: Bootstrap records a followable source

- **GIVEN** a concept mined from commit `abc123` on `src/a.py`
- **WHEN** it is written
- **THEN** `sources` contains an object whose `resource` identifies that commit or file
- **AND** `sources` is not a list of strings

#### Scenario: String sources are not accepted as the stored form

- **GIVEN** incoming frontmatter `sources: ["commit:abc"]`
- **WHEN** the concept is parsed for write
- **THEN** the engine either rejects the write with a reason naming `sources`
- **OR** rewrites the entry to an object with `resource` before storing
- **AND** the stored file is not a YAML list of scalars under `sources`

### Requirement: Actors follow the OKF convention

`generated.by` and `verified[].by` SHALL use `<producer>/<version>` for agents, `human:<id>` for people, and `process:<id>` for automated processes. The prefix `agent:` SHALL NOT be written. Trust tiers MAY be derived from the `human:` prefix as OKF specifies; they SHALL NOT affect the required pin check.

#### Scenario: An agent-authored concept uses producer/version

- **GIVEN** a concept generated by Cursor Grok
- **WHEN** it is serialized
- **THEN** `generated.by` matches the producer/version form
- **AND** it does not start with `agent:`

#### Scenario: Process attest does not use a human actor

- **GIVEN** the ripgrep engine
- **WHEN** an actor string for that engine is required
- **THEN** it is `process:repocodex-rg` (or another `process:` id)
- **AND** it is not stored as `verified` solely because a pin check passed

### Requirement: Absent status means stable

When `status` is omitted, the concept SHALL be treated as `stable`, matching OKF. `draft` remains valid when explicitly set (bootstrap). The write gate SHALL NOT rewrite an omitted status to `draft`.

#### Scenario: Minimal concept is stable

- **GIVEN** frontmatter containing `type` and `verification` but no `status`
- **WHEN** the concept is parsed
- **THEN** its status is `stable`

### Requirement: Unknown types and extra keys survive round-trip

The schema SHALL NOT enumerate OKF types as a closed set that rejects the document. RepoCodex MAY still *author* `TechnicalDecision`, `InvariantContract`, `BusinessWorkflow`, and `GuardrailDecision`. A consumer load SHALL keep unknown `type` values and unknown keys.

#### Scenario: GuardrailDecision still writes

- **GIVEN** a GuardrailDecision with anchors on an enforcement config
- **WHEN** it is written
- **THEN** `type` is `GuardrailDecision`
- **AND** anchors are stored as today

#### Scenario: Extra keys are preserved

- **GIVEN** a concept with an unknown frontmatter key `owner: billing`
- **WHEN** it is parsed and serialized
- **THEN** `owner: billing` is still present

### Requirement: Reverse index lives beside metrics, not in the bundle

The generated path→concept map SHALL be written at `.repocodex/reverse-index.md` for the repo-root bundle and at `.repocodex/reverse-index/<escaped-context-parent>.md` for each shard. It SHALL NOT be written under `.context/`. Regeneration SHALL remove any leftover `.context/**/reverse-index.md`. Unanchored concepts SHALL NOT appear in the map.

#### Scenario: Root reverse index is outside .context

- **GIVEN** an accepted write that pins a source file in the repo-root bundle
- **WHEN** the reverse index is regenerated
- **THEN** `.repocodex/reverse-index.md` contains that path→concept mapping
- **AND** `.context/reverse-index.md` does not exist

#### Scenario: Shard reverse index is one file per context root

- **GIVEN** a mirrored `.context/` under `packages/billing/`
- **WHEN** the reverse index is regenerated
- **THEN** the mapping is at `.repocodex/reverse-index/packages-billing.md`
- **AND** `packages/billing/.context/reverse-index.md` does not exist
