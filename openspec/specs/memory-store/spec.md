# memory-store Specification

## Purpose

Store executable memory as an OKF v0.2 bundle at `.context/`: one markdown file per concept, typed frontmatter, a generated reverse index, and optional monorepo sharding so package-local concepts land in the shard that owns their pins.

## Requirements

### Requirement: OKF v0.2 concept bundle

The system SHALL store memory as an OKF v0.2 bundle at `.context/`, one markdown file per concept, where concept identity is the file path relative to `.context/` (without `.md`) and the markdown body carries the prose why.

#### Scenario: Concept written to the bundle

- **GIVEN** an agent has a why to record for `src/billing/PaymentGateway.ts`
- **WHEN** `repocodex write` accepts the concept
- **THEN** a single markdown file is created under `.context/` with OKF frontmatter (`type` required)
- **AND** the directory `index.md` catalog and `log.md` are updated in the same operation

#### Scenario: Unknown frontmatter keys are preserved

- **GIVEN** a concept containing producer-defined extension keys
- **WHEN** any RepoCodex component rewrites the file
- **THEN** unknown keys are preserved byte-for-byte per OKF conformance

### Requirement: Concept types

The system SHALL support four concept types — `TechnicalDecision`, `InvariantContract`, `BusinessWorkflow`, and `GuardrailDecision` — and SHALL reject any concept, of any type, that lacks a passing anchor.

#### Scenario: Workflow concept spans packages

- **GIVEN** a business flow touching `api`, `billing`, `ledger`, and `notify` packages
- **WHEN** an agent writes a `BusinessWorkflow` concept
- **THEN** the concept carries one anchor per participating site, each attesting independently

#### Scenario: Guardrail concept pins enforcement config

- **GIVEN** a negative architectural rule enforced by import-linter
- **WHEN** an agent writes a `GuardrailDecision` concept
- **THEN** the concept anchors the enforcing tool's config file, so weakening the rule drifts the anchor

### Requirement: Frontmatter extensions

The system SHALL define and validate the extension fields `verification` (required), `claims` (required when prose states checkable literals), `supersedes` and `rationale` (required on why-change), and a bundle-level `format_version`.

#### Scenario: Why-change without supersedes is rejected

- **GIVEN** an existing stable concept whose why is being changed
- **WHEN** the agent writes the replacement without `supersedes` and `rationale`
- **THEN** the write is rejected with a machine-readable reason

### Requirement: Committed reverse index

The system SHALL maintain `.context/reverse-index.md` as a generated, committed artifact mapping source paths to concept paths, regenerated by the engine on every accepted write or reanchor.

#### Scenario: Index stays in sync

- **GIVEN** an accepted `repocodex write` that adds a new pinned path
- **WHEN** the write completes
- **THEN** the reverse index includes the new mapping in the same change

#### Scenario: Out-of-sync index fails CI

- **GIVEN** a PR whose anchors and reverse index disagree
- **WHEN** the required CI check runs
- **THEN** the check fails with an index-sync error

### Requirement: Monorepo sharding

The system SHALL support `.context/` directories that mirror the source tree, with package-local concepts stored near the packages they pin, cross-cutting pages at the root, and per-shard reverse indexes.

#### Scenario: CI attests only affected packages

- **GIVEN** a monorepo with sharded `.context/` directories
- **WHEN** a PR touches files in one package
- **THEN** validation attests only concepts whose pinned paths intersect the diff

### Requirement: Accepted writes land in the owning shard

The system SHALL write each accepted concept into the `.context/` shard that owns its pinned paths — the deepest mirrored bundle whose directory contains them — rather than always into the shallowest discovered bundle, and SHALL place cross-cutting concepts whose pins span shards at the root bundle. The reverse index of the receiving shard SHALL be regenerated on acceptance.

#### Scenario: Package-local concept lands in the package shard

- **GIVEN** a monorepo with a `.context/` bundle at the root and another mirroring `packages/billing/`
- **WHEN** a concept pinning only files under `packages/billing/` is accepted
- **THEN** the concept file is written into the `packages/billing/.context/` shard
- **AND** that shard's reverse index includes the new mapping

#### Scenario: Cross-shard concept lands at the root

- **GIVEN** a `BusinessWorkflow` concept with anchors in two different shards
- **WHEN** the write is accepted
- **THEN** the concept is written to the root bundle and each affected shard's reverse index reflects its pins
